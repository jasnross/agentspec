1. Consider deriving id from path instead of requiring in frontmatter
   - Currently `id` is a required `String` in all frontmatter structs; missing it causes a parse error at load time
   - `id` is used for two things: duplicate detection in validation, and output filename/dirname construction in every adapter
   - The file path already encodes a natural identity: the stem for agents and rules (`agents/foo.md` → `foo`), the directory name for skills (`skills/foo/` → `foo`)
   - Deriving id from path would eliminate redundant frontmatter, prevent path/id mismatches, and make the path the single source of truth
   - The open question is whether callers ever legitimately want the output filename to differ from the source filename; if so, `id` (or a rename field) remains useful as an override

   - Claude supports running skills in forked subprocesses via frontmatter fields
   - OpenCode has a similar concept for command execution
   - Currently neither adapter emits the relevant frontmatter to enable this
4. Orphan cleanup for merged JSON entries when a sync target is removed
   - Sentinel-based ownership in `hooks_merge` only cleans up `_agentspec_id` entries when agentspec runs the merge for that provider
   - If a user removes `[sync.claude]` from `agentspec.toml` (or deletes all hook specs and the sync target), the next `sync` skips Claude entirely — previously-injected entries persist in `settings.json` as permanent orphans
   - The manifest layer handles the equivalent for files via per-destination `.agentspec-manifest.json` cleanup, but `settings.json` isn't manifest-tracked
   - Likely shape: an `agentspec sync --prune` (or `unmerge`/`uninstall`) subcommand that walks all candidate `settings.json` / `hooks.json` paths and strips agentspec-tagged entries
   - Out of scope for the hooks-pipeline branch; revisit before 1.0
5. Support sharing spec content (helper scripts, fragments) across multiple agentspec spec directories
   - Intra-`spec/` sharing via symlinks is now supported: the load phase follows symlinks within `sources_dir`, resolves them to target content, and emits regular files in compiled output. The remaining scope is cross-`spec/`-directory sharing only.
   - Use case: a user has two separate spec directories (e.g., work and personal) that share common hook scripts or `{% include %}` fragment files; today they must duplicate these across directories
   - Two candidate approaches: (a) agentspec follows symlinks during the load/walk phase, resolving them to their real content and copying that content into synced output — no config change required, but symlink semantics may be surprising across OS/VCS boundaries; (b) a new `[spec].extra_dirs` (or similar) config key lists additional root directories whose contents are merged into the spec search paths at load time, making sharing explicit and portable
   - Open questions: does sharing apply only to fragment/supporting files, or also to full agent/skill/rule/hook specs? How do id collisions resolve when the same spec id appears in two roots? Does the manifest track provenance (which root a file came from) so `remove` knows which entries are local vs. shared?
   - Cost: `AdapterOutput.patches` and `RemovalOutput.patches` become two distinct types; sync_plan/remove_plan signatures change; existing patches' construction-site code is fine but the boxing types need the new trait names
   - Surfaced by Pass 3 of the adapter-trait-api-consolidation review. Defer until the next adapter-API touch lands; not blocking for the current branch
6. Consider how to support provider-specific specs in general (hooks and beyond)
   - The hook payload translation shim (`thoughts/ideas/2026-05-10-agentspec-hook-payload-translation-shim.md`) intentionally ships v1 with no per-hook canonicalization opt-out — every emitted hook command points at the wrapper, every wrapper canonicalizes. This keeps v1 scope bounded but leaves provider-specific hooks (Claude's `effort.level` reads, Cursor's `subagent_model` reads, anything depending on `defer` / `followup_message` / `WorktreeCreate` plain-stdout / `failClosed`) reachable only through the canonical `provider_raw` escape hatch — usable for inputs, but provider-only output features remain out of reach
   - Same gap exists in spirit for other spec kinds: a Claude-only agent or Cursor-only skill has no first-class way to declare "only emit me for this provider" today; the workaround is per-provider sync targets which is coarse-grained
   - Likely shape: a per-spec `provider_specific = "claude" | "cursor" | "opencode"` (or list) frontmatter field that compile/sync respects across all spec kinds. For hooks, `provider_specific` would also bypass wrapper generation. For agents/skills/rules, it gates emission
   - Open questions: cross-provider sync-target validation (load-time error vs. silent skip when a spec targets a provider that isn't an active sync target); manifest interaction (does the spec count toward provider-N's owned-files set even when not emitted?); interaction with prefixing/AdapterConfig; whether the field name should be singular (`provider_specific`) or list (`providers`) for the multi-provider case
   - Out of scope for the hook-payload-translation-shim branch; revisit when one of: (a) someone hits the missing escape hatch in practice, (b) a provider-only spec kind comes up that can't be expressed as a hook
7. Auto-install `jq` for plugin-mode hooks via the plugin persistent-data directory
   - v1 of the canonical hook payload shim (plan `thoughts/plans/2026-05-10-agentspec-hook-payload-translation-shim.md`) treats `jq` as an external prerequisite — if it isn't installed on the user's machine, the shim prints a clear error and exits non-zero. This works but pushes a small one-time install onto plugin end users
   - Both providers already expose a writable, persistent-across-updates per-plugin directory: Claude Code's `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/{id}/`, documented at https://code.claude.com/docs/en/plugins-reference#persistent-data-directory) and Cursor's `${CURSOR_PLUGIN_DATA}` (path undocumented; injected only into plugin hooks). Both substrates landed before this TODO was written
   - Likely shape: a `SessionStart` shim that follows the Claude Code docs' manifest-diff-and-reinstall pattern (compare a bundled `jq.sha256` manifest against a copy in the data directory; download + verify on mismatch). One bootstrap script per provider, parameterized by platform/arch via `uname -sm`. SHA256s are stamped into the generated bootstrap script by agentspec at sync time, sourced from upstream jq release attestations
   - Platform handling: linux-amd64, linux-arm64, darwin-amd64, darwin-arm64. macOS downloads must strip the `com.apple.quarantine` xattr (`xattr -d com.apple.quarantine "$JQ"`) before exec — without this, Gatekeeper silently fails the exec
   - Failure-mode design: if the download fails (offline, captive portal, firewall), the bootstrap exits non-zero with a clear stderr message pointing at the manual `brew install jq` / `apt install jq` fallback. Subsequent shim invocations in the same session see the missing `jq` and fail loudly per v1 behavior

24. Settle the harness's stance on `PROBE_FIXTURE` and unreachable discriminator fixtures
    - **The question.** A probe package's discriminator fixture proves the assertion discriminates, but nothing runs it after authoring time. Should a package be required to expose it through a code path, or is the contract's saved-view route sufficient?
    - **The harness is currently split.** `claude-agent-effort/probe.sh` and `claude-skill-effort/probe.sh` read `PROBE_FIXTURE` (and `PROBE_DRY_RUN`) so any arm can be re-run; the other nine runners hardcode the assertion arm. `opencode-agent-variant/`, `opencode-skill-frontmatter-discard/`, and `opencode-command-variant/` all commit a `fixtures/discriminator/` no code path reaches, and `cursor-subagent-model-options/` commits no discriminator at all — its refuting arm exists only as a gitignored capture
    - **Both positions have contract text behind them, which is why review keeps landing on it.** `experiments/README.md` authoring step 5 endorses re-evaluating a candidate projection against a saved view — `record.sh --manifest <probe.json> --view <saved-view> --dry-run` — with no runner involvement at all.     - **Question.** Does Cursor parse a `[context=…]` bracket option in subagent frontmatter and apply it to the resolved model? Measured 2026-08-24 against **Cursor 3.17.8**: no oracle Cursor exposes can tell
    - **Why it matters — revised 2026-08-26, and it no longer blocks anything.** This entry originally read that an unverifiable `context` blocks Set 2 of the effort-in-execution-presets design, because that design's unconditional ban on hand-written brackets was thought to require every documented Cursor option to be _verified_. The ban's actual premise is that every documented option stays _expressible_. A named preset field satisfies that for `context`, but not in general: Cursor's bracket options are the SDK's model parameters, whose ids vary by model and are account- and team-specific, so a fixed set of named fields cannot cover them. Expressibility is carried by `CursorPreset.params`, an escape-hatch map; the named fields are only the subset agentspec types and documents. The design now ships `CursorPreset.context` on Cursor's published syntax and disclaims the option's effect under its satisfiability boundary, the same boundary that already covers `effort = "xhigh"` against a model that silently clamps it
    - **What an oracle would still buy.** Not a design change — the field ships either way. It would close the one link in that design's four-link chain where `context` stops short of `effort` and `fast`: whether Cursor carries the option into its own resolved view, or discards it as an unknown key. Today those two are indistinguishable. An oracle would also settle whether the pass-through is worth documenting as working rather than as merely harmless
    - **What was tried.** Arms in a live Cursor session against a `subagentStart` capture hook, each with a bare-model baseline under the same `subagent_type`:
      - `claude-opus-5` (baseline) resolved `claude-opus-5-thinking-high`
      - `claude-opus-5[context=300k]` resolved `claude-opus-5-thinking-high` — indistinguishable from the baseline
      - `claude-opus-5[context=1m]` resolved `claude-opus-5-thinking-high` — indistinguishable, so the result is not magnitude-specific
      - `claude-opus-5[effort=low,context=300k]` resolved `claude-opus-5-thinking-low` — `effort` rendered, `context` absent, so it does not surface alongside another option either
    - **The structured payload is out of reach.** `model_params` is the only structured resolved-parameter payload Cursor exposes, and it appeared on exactly one of ten `beforeSubmitPrompt` events, describing the **parent** turn's own settings (`effort=high, fast=false`). Every one of ten `subagentStart` payloads — nine distinct arms, one invoked twice — carried `model_params: null`. `.model` and `.subagent_model` are identical on that event, so the parent field is no second oracle either
    - **This is not the same as "context is ignored."** The flattened `subagent_model` hides an option whose value equals the model's default, which is what invalidated two arms in the original Cursor round and what makes `fast=false` invisible here too. A silent `context` is consistent both with Cursor dropping it and with Cursor applying it invisibly. Distinguishing them needs an oracle that does not exist today
    - **Where to look next.** A model family where `context` is non-default (as `fast` turned out to be model-coupled — it rendered on `claude-opus-5` and `grok-4.6` but `effort` did not render on `composer-2.5`); or any Cursor event not yet enumerated that carries `model_params` for a subagent. Cursor's outbound request is unobservable in principle, so no probe on this surface can ever exceed `resolved-config`
    - **No package exists** because a package is a measurement and this measured nothing. Whoever finds an oracle authors the manifest, the assertion, and the runner together
    - **`cursor-subagent-bracket-tolerance` does not discharge this entry**, and the two are easy to confuse. That package asks a different and reachable question — does a bracket carrying an option the oracle cannot see still apply the options it can — asserting `claude-opus-5[effort=low,context=300k]` → `claude-opus-5-thinking-low`. It measures that `context` is _harmless_, never that it is _honored_. This entry stays open when that one lands
    - Raised by `$THOUGHTS_DIR/plans/2026-08-23-agentspec-set-0-provider-probe-packages.md` Phase 5, whose stop condition this fired. That stop condition was discharged on 2026-08-26 by a revision of `$THOUGHTS_DIR/designs/2026-08-12-agentspec-effort-in-execution-presets.md`, whose "Format and effect are different claims" section carries the reasoning. Captures preserved at `experiments/.probe-scratch/cursor-explore/` (gitignored, so present only on the machine that ran the session)

29. Consider failing closed in the Cursor adapter's bracket composition

31. `CursorPreset.params` values are string-only
    - A bracket option whose value is a boolean or a number has no expression through `params`: `params = { n = true }` is a parse error naming `presets.<name>.cursor.params.n`. The named fields cover the typed cases agentspec knows about (`fast` is a `bool`), but an _unknown_ option with a non-string value is stuck
    - Low priority — every Cursor option id documented today takes a string or a bool, and the bool one has a named field. Revisit if a numeric parameter appears in `Cursor.models.list()`
32. `NAMED_CURSOR_OPTIONS` drift is only half-guarded
    - `test_named_cursor_options_are_real_fields` round-trips each entry through `deny_unknown_fields`, so a **rename or removal** fails the test. A field **added** to `CursorPreset` and left out of the array is not caught — at which point `params.<newfield>` would re-spell it and compose the option twice
    - Rust has no field-name reflection without a macro, which is why this is a stated limit rather than a covered case. The array's doc comment says so

34. Reevaluate the warnings system as a whole — one surface, and stop repeating expected warnings
    - **The problem.** Degradations are permanent structural facts, not news. "This Cursor skill cannot carry preset values" is equally true on the first sync and the hundredth, so emitting it every time trains the reader to skim the diagnostic block — which costs attention to the warnings that _did_ change (`ParityWarning`, the ignore-pattern-matched-nothing warning). The goal is a surface a user consults to learn the state of things, not a stream pushed at them
    - **Two goals.** (1) One surface handling the "warning" concerns, so adapters stop being responsible for asserting them; (2) stop pushing completely expected warnings to users
    - **The architectural idea: adapters report facts, the orchestrator derives judgments.** Today an adapter reports both what it emitted _and_ the assertion "I dropped something here." If adapters instead returned a structured record of what they put where, the orchestrator could derive the loss by comparing that against resolved intent. The design's own condition is already phrased as exactly that comparison — "a value the author typed reaches no file emitted for this provider" — so no adapter knowledge is needed to evaluate it. This deletes a class of thing each adapter must get right, and a fourth provider would no longer have to narrate its own omissions
    - **Why a summarized view earns its place over just reading generated output.** The interesting quantity is a _delta_, and the artifact cannot show it: the absence of a `variant:` line in a generated OpenCode skill file is invisible unless you already know a preset was supposed to supply one. Nothing in the output records the intent it failed to carry
    - **Hard bound on what such a surface may claim: link 1 only.** It can report what agentspec delivered into a file. It can say nothing about whether the provider honors it — Claude drops a skill's `effort` on model-invoked paths, Cursor composes `inherit[effort=high]` and warrants nothing, and OpenCode discards a variant whenever the session's model differs from the agent's declared one (verified in OpenCode source at `cc4b456`, unchanged at HEAD; recorded in the design's satisfiability boundary and in `README.md`, unmeasured by any probe). A view that renders "delivered ✓" beside those reads as "working" and is worse than no view. Scope and label it against the four-link chain in `$THOUGHTS_DIR/designs/2026-08-12-agentspec-effort-in-execution-presets.md`
    - **It will not subsume everything, so "one surface" is partly aspirational.** `PartialOutputImpl` is a claim about agentspec's own completeness rather than a dropped value; `ParityWarning` compares providers against each other and no per-file derivation produces it; the load-stage ignore-pattern warnings are a different stage entirely. Expect to consolidate the degradation class cleanly and still have other diagnostics
    - **It is not a smaller codebase.** Deletes `DegradationKind`, `presentation()`, the per-adapter push sites, and the `BTreeSet` drain; adds a structured emission record, a derivation pass, and a report renderer. The win is responsibility, not line count — say so up front so the work is not sold as a reduction
    - **This absorbs Set 3 of the effort-in-execution-presets design, whose two diagnostics turn out to be different classes.** The skills diagnostic (a skill named a preset configuring execution that no file emitted for that spec can carry) is the canonical case for the new surface and should _not_ ship as a `DegradationKind`. Constraint 1's OpenCode half (a preset sets `variant` with no `model`) is not an output question at all — it is a config-shape fault like the existing unknown-preset error, genuinely actionable and low-volume, and could ship independently. Both are deferred here rather than split, because adding a validate-time warning channel immediately before a consolidation design means the consolidation gets designed around a channel just added rather than around what is needed
    - **Two findings worth not re-deriving.** A provider-level capability accessor cannot express the skills condition — the design establishes this with two fixtures that land on opposite rows of the same accessor. And `opencode debug agent` cannot measure the model-less-variant question: it reports resolved _agent config_, which shows `variant` either way, because the discard happens one layer below in `createUserMessage` and needs a live session. Do not author a package against that oracle
    - **Shipping without this costs users nothing they have today.** `README.md` already carries "Execution presets reach skill files on Claude only" as prominent prose, and the design states the diagnostics were always the narrow refinement on top of that rather than the primary channel
    - Raised 2026-08-31, during Set 3 planning for `$THOUGHTS_DIR/designs/2026-08-12-agentspec-effort-in-execution-presets.md`
